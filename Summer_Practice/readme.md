# Summer Practice 2026: Second-Year Students

Practice type: Manufacturing Practice  
Period: 29.06.2026-25.07.2026  
Format: one weekly meeting, offline / online  
Work mode: individual project  
Supervisor: Nazih Errahel

## Goal

You will build a small but complete software product and defend it at the end of the practice.

Your project must focus on software development technologies: requirements, architecture, Git, implementation quality, testing, documentation, and deployment or clear run instructions.

Do not choose computer vision, AI, or machine learning as the main topic. Those topics are for later study. If you use an external AI tool or API, it must be optional and not the main project value.

## Required Documents and Results

You must submit:

- final report following the official requirements;
- title/task page;
- journal list;
- characteristic template;
- project code or repository link;
- defense slides with demo evidence, such as screenshots, deployed link, API screenshots, or working prototype.

Your report must include at least 10 sources unless the department gives a stricter rule.

Your final report should contain these core sections:

- introduction;
- literature review / background;
- requirements and architecture;
- implementation;
- testing and results;
- discussion of problems, limitations, and possible improvements;
- conclusion;
- reference list.

## Topic Rules

You may choose one topic from the list, modify one, or propose your own topic for supervisor approval.

Your topic must have:

- a real problem or user scenario;
- clear users;
- main software features;
- a database, file storage, or external API if needed;
- basic tests or testing evidence;
- README and run/deployment instructions.

## Suggested Topics

### SD-01: Small Team Task Management System

Scenario: A small team needs a simple system to organize projects, tasks, deadlines, priorities, and responsible members.

Expected result: web app or API with frontend, simple user roles, task status workflow, database, README, and run/deployment instructions.

### SD-02: Student Submission Tracking System

Scenario: A teacher or supervisor needs to track student reports, journal files, slides, and links to code in one place.

Expected result: student and supervisor roles, file/link submission workflow, status tracking, deadline indicators, and Docker Compose setup.

### SD-03: Equipment Booking System

Scenario: A university lab wants students to reserve cameras, laptops, sensors, or rooms.

Expected result: booking calendar or reservation table, conflict prevention, approval workflow, equipment status, and basic tests.

### SD-04: Inventory Management for a Small Shop

Scenario: A local shop needs to track products, stock quantity, suppliers, and sales.

Expected result: CRUD operations, search/filtering, low-stock warnings, supplier records, database seed data, and containerized run instructions.

### SD-05: Course Lab Submission Tracker

Scenario: A teacher needs to track lab submissions, screenshots, grades, and feedback.

Expected result: student list, lab list, submission status, feedback field, simple grade summary, and CSV/PDF export if possible.

### SD-06: REST API for Event Registration

Scenario: A student club organizes events and needs registration, participant lists, and check-in.

Expected result: REST API, documented endpoints or OpenAPI/Swagger, event capacity limits, participant search, endpoint tests, and Docker support.

### SD-07: CLI Automation Tool for Report Checks

Scenario: Students submit folders with code, screenshots, and documents. A supervisor wants a tool that checks the folder structure and missing files.

Expected result: command-line tool, configurable required files, clear console output, generated summary report, and unit tests.

### SD-08: Simple Helpdesk / Ticket System

Scenario: An IT support team needs to receive, assign, and close support requests.

Expected result: ticket creation, priority/status workflow, assignee field, comments/history, search/filtering, and basic dashboard.

## Defense

Your defense should include:

1. Title, student name, supervisor, and practice type.
2. Problem and motivation.
3. Target users or application scenario.
4. Proposed solution.
5. Requirements.
6. Architecture and technologies.
7. Implementation process.
8. Results/demo shown during defense.
9. Testing and deployment/run instructions.
10. Difficulties and limitations.
11. What was learned and next steps.
